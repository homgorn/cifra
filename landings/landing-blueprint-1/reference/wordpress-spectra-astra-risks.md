# Spectra + Astra + WP All Import — риски и факты (реальный ресёрч, не домыслы)

Собрано из: форума поддержки WP All Import, форума GeneratePress (живой кейс с
UAGB/Spectra), исходников Astra, и open-source проекта
`wpformation/claude-skill-astra-spectra` (MIT, 11★, детально документирует
Spectra на базе реального продакшен-опыта — 24 задокументированных «ловушки»).
Ссылки — внизу файла.

## Риск №1 (главный) — импортированные блоки Spectra рискуют остаться без стилей

**Факт**, подтверждён тремя независимыми источниками:
- Официальный ответ автора плагина WP All Import на форуме поддержки: плагин
  не имеет отдельного UI для Gutenberg-блоков — блоки нужно вставлять как
  сырой HTML (`<!-- wp:... -->` комментарии) в поле контента. Это именно то,
  что делает `render-wp.js` — тут всё ок.
- НО: Spectra/UAGB генерирует CSS для своих блоков **динамически, при
  сохранении страницы через редактор Gutenberg** (плагин сканирует контент
  поста на save-хуке и кладёт результат в кэш/файл). Живой кейс с форума
  GeneratePress: разработчик вставил UAGB-блок не через редактор, а через
  сторонний механизм — стили на фронтенде не подгрузились, и в поддержке
  прямым текстом подтвердили: *«there isn't anything we can do about that»*.
- Проект `claude-skill-astra-spectra` называет это «Quirk» и для своего
  REST-API пайплайна (POST через `wp/v2/pages`) добавляет обязательный шаг
  **«force regen Spectra» с 4 каскадными стратегиями** (mu-plugin → нативный
  endpoint → trick с временной публикацией → ручной) именно потому, что без
  этого шага CSS не появляется.

**Вывод:** массовый импорт через WP All Import (XML/CSV → `post_content`,
без прохода через сам редактор) — это ТОТ ЖЕ сценарий, что сломался в кейсе
выше. Десятки лендингов могут после импорта выглядеть неотформатированными,
пока по каждой странице не «пройтись» (открыть в редакторе и нажать
«Обновить» — или найти программный эквивалент регенерации).

**Почему `render-wp.js` в этом блюпринте использует в основном CORE-блоки
WordPress, а не блоки Spectra** — теперь это не осторожность вслепую, а
прямое следствие риска №1: у core-блоков (`core/heading`, `core/paragraph`,
`core/columns` и т.д.) CSS — часть `wp-includes`/темы, не генерируется
по требованию на каждой странице, поэтому у них этой проблемы нет в принципе.
Если всё же нужны именно блоки Spectra — см. «Что можно сделать» ниже.

## Риск №2 — Astra Global Colors: слоты «гарантированные» и «вариативные»

Astra даёт 9 глобальных цветовых слотов (`--ast-global-color-0` …
`--ast-global-color-8`): Brand, Alternate Brand, Headings, Text, 4 фоновых,
1 вспомогательный (подтверждено официальной документацией Astra). Если
решите завести дизайн-токены именно через Astra Customizer (а не хардкодить
CSS, как сейчас делает `styles.template.css`), учтите задокументированную в
`claude-skill-astra-spectra` ловушку: слот `color-7` на части пресетов по
умолчанию равен чёрному — если какой-то блок жёстко завязан на «слот 7», а
не на ваш реальный бренд-цвет, можно случайно получить чёрный текст/фон там,
где не ожидали. Перед массовым использованием слотов — проверить фактический
резолв конкретно на вашей установке (в referenced проекте есть для этого
`scripts/resolve-palette.php`).

## Риск №3 — у Spectra/UAGB есть блок FAQ, но под другим именем поля

В Spectra (экс-UAGB, namespace `uagb/`) действительно есть встроенный
FAQ/Accordion блок со schema-разметкой (а не только core/html, как сейчас в
`render-wp.js`). Задокументированная в том же проекте ловушка: если указать
атрибут `description` вместо `answer` — блок отрендерит Lorem Ipsum вместо
вашего текста. В `render-wp.js` этого блока пока НЕТ — используется честный
`core/html` с `<details>/<summary>`, что гарантированно работает, но не даёт
встроенной Schema-разметки от самого блока (JSON-LD FAQPage у нас уже
генерируется отдельно в `render.js`/`render-wp.js`, так что schema всё равно
есть — просто не через нативный блок).

## Риск №4 — хостинг-ловушки (если шаред-хостинг для Node бэкенда или самого WP)

Задокументированы для o2switch/OVH/Hostinger: срезание заголовков
Application Passwords (если захотите автоматизировать публикацию через
REST API с паролем приложения — некоторые шаред-хостеры режут этот заголовок
на уровне сервера), и конфликты LiteSpeed-кэша с регенерацией CSS Spectra
(кэш отдаёт старую версию страницы без свежих стилей). Если ваш WP-хостинг —
из этого списка или похож по конфигурации, это дополнительная причина
тестировать один реальный импорт перед массовым прогоном.

## Риск №5 (отдельный, не про Spectra) — Node-бэкенд и типичный WP-хостинг

`backend/server.js` — это Node.js/Express процесс. Обычный шаред-хостинг под
WordPress (там же, где крутится сам WP на PHP) в большинстве случаев НЕ умеет
держать постоянный Node-процесс. Варианты: (а) отдельный хостинг для Node
(VPS/Railway/Render/Vercel-функция) и фронтенд обращается туда по абсолютному
URL с настроенным CORS; (б) переписать логику приёма лида как WP REST API
endpoint на PHP (`register_rest_route`) — тогда она живёт прямо в WP и этот
отдельный вопрос с хостингом Node снимается целиком, но требует переноса
логики `server.template.js` на PHP. Этот блюпринт пока даёт только вариант (а).

## Что можно сделать (не сделано сейчас, требует вашего решения)

1. Принять риск №1 как есть (текущее решение: core-блоки + один `wp:html` для
   квиза) — ничего дополнительно не требуется, работает сразу после импорта.
2. Либо добавить пост-импортный шаг «регенерации» — для этого нужен
   WP-CLI доступ или REST API с Application Password на целевом сайте,
   которого у меня в этой сессии нет и который я не стал имитировать.
3. Для настоящих блоков Spectra (`uagb/*`) вместо core — нужны их реальные
   JSON-атрибуты по каждому блоку; у проекта `claude-skill-astra-spectra`
   это есть (`references/spectra-blocks-catalog.md`, 49 блоков), но сам файл
   я не читал построчно (вне бюджета этой сессии) — можно сделать отдельным
   шагом, если решите, что риск №1 того стоит.
