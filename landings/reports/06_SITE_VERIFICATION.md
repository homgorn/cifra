# Проверка сайта клиента: что подтвердилось, что опроверглось

Дата: 2026-10-03. Проверка прямыми запросами к цифра18.рф, не по
поисковым сниппетам и не по документации блюпринта.

Итог: пять утверждений блюпринта неверны, одно из них меняло план
работ. Ниже доказательства.

## 1. Сайт доступен, robots.txt не блокирует

Было записано в `README.md` блюпринта и в `00_HANDOFF_LANDINGS.md`:

> «прямой fetch страницы блокирует robots.txt сайта»
> «Каталог в config.example-2 собран по поисковому сниппету, а не по
> странице: robots.txt сайта блокирует прямой fetch»

Фактически robots.txt отдаёт:

```
User-Agent: *
Allow: /
Crawl-delay: 3
```

`Allow: /` означает разрешение обхода всего. Сайт отдаёт и HTML, и
картинки, и sitemap.

Откуда взялся таймаут: домен `цифра18.рф` в кириллице не резолвился
в этой среде, punycode-форма работает сразу. Проверка:

```
xn--18-6kc5a3bxam.xn--p1ai   ← работает
Test-NetConnection :443       ← True
```

**Следствие.** Каталог в демо-конфиге можно заменить настоящими
данными. Дальше и выкачка, и проверка фактов делаются прямо с сайта.

Правило поведения взято из самого robots.txt: `Crawl-delay: 3`,
задержка между запросами в скрапере выставлена 3 секунды. Это сайт
клиента, нагрузку не создаём.

## 2. Ссылки на VK и MAX настоящие

Было записано:

> «vk.com/cifraprint18 и max.ru/id182501416864_bot в демо. Рабочих
> ссылок у автора не было, сайт не даёт их спарсировать. То есть
> откуда-то они взялись, но источник не документирован.»

Фактически обе ссылки стоят **в футере самого сайта клиента**,
рядом с телефоном и почтой:

```html
<a href="https://vk.com/cifraprint18"></a>
<a href="https://max.ru/id182501416864_bot"></a>
```

Правило чек-листа «ни одной ссылки, которую не видел вживую»
выполнено: ссылки видны вживую, на сайте клиента. Используем.

## 4. Счётчик Метрики подтверждён

В разметке сайта, внутри блока Яндекс.Метрики:

```js
ym("50863157", "init", { clickmap: true, trackLinks: true, ... })
```

Совпадает с `METRIKA_COUNTER_ID` в `.env`. Значит правка целей
Метрики из `03_INSTRUCTIONS.md` верна: номер 50863157, а не
12345678, который зашит в `script.template.js`.

## 5. Политика персональных данных отдаёт 404

Ты просил найти правильный URL в sitemap. Нашла в футере, но он
не работает.

Ссылка в футере сайта:

```html
<a href="/sogl/">Соглашение об обработке персональных данных.</a>
```

Проверка:

| Путь | Код |
|---|---:|
| `/sogl/` | **404** |
| `/sogl` | **404** |
| `/politika/` | 404 |
| `/privacy/` | 404 |
| `/politika-konfidencialnosti/` | 404 |
| `/legal/` | 404 |
| `/politika-obrabotki-personalnyh-dannyh/` | 404 |
| `/agreement/` | 404 |

В sitemap её нет: 13 инфоблоков плюс `sitemap-files.xml`, ни один
не содержит страницы согласия.

**Что это значит.** Сейчас сайт собирает персональные данные через
формы и ведёт на страницу, которой не существует. Это риск: нет
документа, на который сослаться, и РКН может задать вопрос.

**Что надо сделать.** Создать одну страницу соглашения на весь домен,
заменить ссылку в футере, положить её в sitemap. Шаблон уже есть в
блюпринте: `templates/privacy.template.html`, 85 строк, девять
разделов под 152-ФЗ. Реквизиты ИП известны.

Лендинги ссылаются на эту единую страницу. Не на тридцать копий.

## Вывод для плана

значит, что фактчекинг из предположительного становится проверяемым,
и каталог лендингов можно строить на настоящих позициях.
