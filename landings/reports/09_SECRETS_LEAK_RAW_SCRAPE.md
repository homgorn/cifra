# Утечка сессионных токенов клиента через сырую выкачку

Дата: 2026-10-04. Обнаружено гейтом `scripts/export/scan_secrets.py`.

## Что случилось

Папка `landings/_scrape/raw/` была закоммичена в git. В ней 457 html-страниц
сайта заказчика, 62,7 МБ. В HTML каждой страницы Битрикс24 лежит `sessid`:
идентификатор сессии посетителя, и в выкачке таких вхождений **2283 в 457
файлах**.

Гейт нашёл это только сейчас, потому что до этого запускался по
`merch-landing-v2` и мерчу, а папка `raw/` в вывод не попадала.

## Три уникальных значения на всю выкачку

| № | Значение | Где лежит на странице |
|---|----------|-----------------------|
| 1 | `a41e…f28a` | `<input type="hidden" name="sessid" value="…">`, три раза на страницу |
| 2 | `ec30…95db` | `var _ba = _ba \|\| []; _ba.push(["aid", "…"])` |
| 3 | `e950…9b5b` | второй вариант `sessid` |

Все три одинаковы во всех 457 файлах, то есть токен один на всю выкачку.
Значения здесь не приводятся целиком: отчёт может попасть в чат или в лог, и
тогда цель чистки будет достигнута ровно на том файле, где осталось проверить,
что токена там нет.

## Что сделано

1. **`landings/_scrape/scrub_raw_tokens.py`** заменяет 32-символьные hex-токены
   на `SESSION_TOKEN_REDACTED_n`, где `n` это номер токена в порядке первого
   появления. Номер нужен, чтобы разные токены остались разными: если
   схлопнуть всё в один плейсхолдер, потеряется информация о том, что значений
   было три, и правка перестанет быть проверяемой.

   Скрипт без `--apply` только отчитывается, с `--apply` чистит и сам же
   проверяет результат повторным чтением. Это важно: сообщение «сделано» по
   факту записи не то же самое, что «токенов не осталось».

2. **Парсер проверен на очищенных файлах.** `fetch_catalog.py --parse-only`
   дал побайтово тот же `catalog.json`: 457 позиций, 31 с ценой, `a == b`
   равно True. Чистка не сломала выкачку.

3. **`/landings/_scrape/raw/` добавлен в `.gitignore`**, файлы убраны из
   индекса командой `git rm -r --cached`. Рабочие копии остались на диске:
   `--parse-only` читает их локально, git для этого не нужен.

4. **Гейт `scan_secrets.py` больше не врёт.** Шаблон `\bym\(\d{4,}\b` ловил
   вообще любой счётчик Метрики и срабатывал на правильном `50863157` в шести
   местах. Счётчик Метрики не секрет: он публично лежит в HTML каждой
   страницы сайта заказчика. Теперь ловится только очевидная заглушка.

## Чего НЕ сделано, и почему

**История git не переписана.** Токены остались в старых коммитах. Убрать их
оттуда можно только перезаписью истории (`git filter-repo`), а это
необратимая операция с общей веткой. Переписывать историю без решения
владельца репозитория нельзя, поэтому решение остаётся за ним.

Пока история не переписана, токен остаётся в клонах. Сессия Битрикс живёт
обычно дни, не месяцы, поэтому практический риск ограничен, но факт
остаётся фактом: значение есть в репозитории.

Что нужно сделать, если решение будет принято:

```
git filter-repo --path landings/_scrape/raw --invert-paths
```

После этого обязательно `git push --force --all`, и всем, кто клонировал,
нужно клонировать заново. Предупреждение: команда переписывает хеши всех
коммитов, поэтому открытые PR и чужие ветки разъедутся.

## Про сам гейт

Гейт нашёл утечку случайно, решая другую задачу: он остановился на
правильном счётчике Метрики, и пришлось разбираться, почему. Это ровно тот
случай, когда шум в гейте приводит к пользе, но только если за шумом
доходят до конца, а не закрывают правило флагом.

Поэтому правило про счётчик не выброшено и не ослаблено до «никогда»:
оно продолжает ловить заглушки, а настоящее значение счётчика проверяет
`landings/validate_landing.py` гейт 4. Гейт 4 при этом починен: он заявлял
«из .env», но сравнивал с литералом, зашитым в код, то есть ничего из `.env`
не читал. Теперь читает `.env` и ловит повторяющиеся цифры.

Проверка на заглушке: подстановка `ym(1111111, "init"` в собранный `index.html`
даёт код возврата 1 и строку `ожидался 50863157, init=['1111111']`.
Восстановление даёт код 0.
