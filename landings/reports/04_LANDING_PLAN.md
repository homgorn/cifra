## Принципы, которые не обсуждаются

1. **Данные только с сайта клиента.** robots.txt разрешает обход,
   сайт отдаёт каталог, цены и фото. Ничего не выдумывается.
2. **Каждая цифра с источником.** Цена ссылается на страницу
   каталога, откуда взята. Ссылка в `CHANGELOG.md`.
3. **Слабые места сайта не наследуются.** Есть битая ссылка на
   соглашение, дубли, отсутствие canonical. На лендингах этого нет.
4. **Ничего лишнего в публичную папку.** Внутренние отчёты с
   разбором багов не публикуются на сайт отчёта.
5. **Один за раз.** Сначала один рабочий лендинг, потом второй.

## Этап 1. Данные с сайта

Состояние: выкачка каталога идёт ночью.

Что делаем:

1. Скрапер обходит sitemap и все страницы каталога, задержка 3
   секунды из `robots.txt`, кладёт HTML в `_scrape/raw/`.
2. Из каждой карточки берём название, цену, описание, свойства,
   фотографии.
3. Отдельно скачиваем фотографии в `_scrape/out/images/`.
4. Собираем `catalog.json` и `catalog.csv`.

Результат: база настоящих позиций с ценами и фото.

Проверка: `summary.md` покажет число страниц, сколько с ценой,
сколько с фото. Если с ценой сильно меньше половины, спросить
клиента, почему.

## Этап 2. Что зависит от аудита ключей

Ты верно заметил, что часть работы связана с семантикой. Это
значит, что она ждёт ключей и не должна блокировать остальное.

| Задача | Ждёт аудита ключей | Почему |
|---|---|---|
| Фото, цены, каталог, свойства | нет | это факты с сайта |
| Каркас лендинга, блоки AIDA | нет | структура от механики, не от слов |
| Микроразметка Schema.org | нет | разметка описывает тип сущности |
| Cookie-баннер, 152-ФЗ, политика | нет | требование закона |
| Тексты УТП | **да** | нужны реальные запросы и ответы на них |
| Заголовки H1 и title | **да** | заголовок это запрос |
| Описания для Директа | **да** | объявление отвечает на запрос |
| Сколько лендингов и какие | **да** | решается по семантике, не по фото |

**Вывод.** Каркас и данные делаем сейчас, тексты и набор страниц
дожидаются аудита. Порядок не нарушается: сначала факты, потом
слова вокруг фактов.

## Этап 3. Первый лендинг: календарь 2027

Приоритет обоснован данными Метрики в `00_HANDOFF_LANDINGS.md`:

- пик сайта в октябре, 2 107 визитов;
- 5 визитов по запросу «календари 2027», спрос уже есть;
- все запросы с двумя и более визитами про квартальный календарь.

На сайте уже есть подтверждённая позиция: квартальный календарь
PREMIUM, прозрачный пластик, от 240 ₽/шт. Значит контент есть.

Что делаем:

1. Забираем из выкачки все позиции раздела «Календари».
2. Собираем `config.json` этого лендинга.
3. Прогоняем `render.js`.
4. Проверяем по чек-листу фактчекинга.
5. Открываем в браузере, тестируем формы руками.

## Этап 4. Приём заявок

Решение: без Node, PHP на сервере сайта.

Причина: сайт на 1С-Битрикс, там PHP. Постоянный Node-процесс на
таком хостинге не поедет, это прямо написано в
`wordpress-spectra-astra-risks.md`, Риск №5.

Три канала доставки, приоритет устойчивости:

1. Битрикс24 Коробка, метод `crm.lead.add`;
2. письмо менеджеру;
3. запись в инфоблок 1С-Битрикс.

Если канал недоступен, заявка всё равно уходит. Если упали все три,
честный отказ вместо тихого успеха.

**Блокирует:** ответ клиента про лицензию и доступ. См.
`02_DECISIONS.md` раздел 7.

## Этап 5. Согласие по персональным данным

Отдельная задача, потому что на сайте она сломана.

Сейчас в футере ссылка `/sogl/`, и она отдаёт 404. В sitemap
страницы нет. Значит форма отправляет персональные данные, а
документа, на который можно сослаться, не существует.

Делаем:

1. Создать страницу соглашения на основе
   `templates/privacy.template.html`.
2. Подставить реквизиты ИП.
3. Заменить ссылку в футере сайта.
4. Добавить страницу в sitemap.
5. Лендинги ссылаются на эту же страницу, копий не делаем.

Проверка: страница открывается, отдаёт 200, есть в sitemap.

## Этап 6. Полное SEO и микроразметка

Без этого лендинг не нужен, задача проекта про продвижение.

Обязательно на каждой странице:

| Элемент | Что сделать |
|---|---|
| title | один, до 60 знаков, содержит услугу и город |
| description | до 160 знаков, призыв, без выдумки |
| H1 | ровно один на страницу |
| canonical | абсолютный URL, сам на себя |
| Open Graph | title, description, image |
| Schema.org | `LocalBusiness`, `Product`, `FAQPage`, `BreadcrumbList` |
| robots.txt | страница разрешена к индексации |
| sitemap | страница в карте сайта |
| alt у картинок | описывает товар, не «фото1» |
| ЧПУ | читаемый адрес, латиницей |

Отдельно про `Product`: цена и наличие в разметке ставятся только
если цены показываются на странице. Разметка не должна обещать то,
чего не видно. Это требование поисковиков, и это же честно.

## Этап 7. Под Директ

Директ требует не только страницы, но и данных для кампании.

Что готовим:

1. УТП каждого лендинга отдельным списком, без приукрашивания.
2. Описания под объявления, написанные под конкретный запрос.
3. Условия показа: гео Ижевск и Удмуртия, интересы по тематике.
4. Страницы отсева, если объявления ведут в разные разделы.
5. События целей в Метрике, чтобы считать конверсии.

**Чего не делаем:** не пишем объявления под запросы, которых нет в
выгрузке Метрики. Клиентский фидбек из `CLAUDE.md`: «Кампании по
внутренним запросам съедают бюджет».

**Блокирует:** данные по ключам из аудита и подтверждение бюджета.

## Этап 8. Превью на сайте отчёта

Цель: увидеть лендинг до публикации на сайте клиента.

Схема: папка `reports/cifra18-audit/demos/`, вне реестра страниц
отчёта.

Почему вне реестра: `validate_report.py` требует, чтобы футер и
нумерация совпадали со списком страниц. Тридцать лендингов в реестре
сломали бы 31 существующую страницу. Вне реестра гейпы их не видят,
а деплой публикует автоматически.

Что делаем:

1. Один каталог лендингов с выпадающим меню.
2. Перелинковка соседей: предыдущий и следующий.
3. Каждая страница лендинга как есть, с фото, cookie-баннером и
  формами.
4. Метки «превью», чтобы не перепутали с рабочей версией.

Обязательное правило: в превью **нет реквизитов ИП**. Футер
заглушен, в поле согласия стоит пометка «превью, не отправляйте
данные». Настоящие реквизиты появятся только на сайте клиента.

## Этап 9. Публикация на сайте клиента

Порядок:

1. Залить папку в директорию сайта.
2. Проверить, что страница отдаёт 200, а не 404.
3. Добавить в sitemap и в меню.
4. Проверить формы: заявка дошла в Битрикс24 и в почту.
5. Проверить согласие по ПДн: ссылка ведёт на существующую страницу.

**Блокирует:** доступ к сайту. Без него готовим папку и инструкцию.

## Порядок приоритетов

1. Данные с сайта: каталог, цены, фото. Блокирует всё остальное.
2. Каркас и микроразметка. Не ждёт никого.
3. Согласие по ПДн. Риск уже существует на сайте клиента.
4. Приём заявок. Ждёт ответа про лицензию.
5. Тексты и набор страниц. Ждут аудита ключей.
6. Директ. Ждёт ключей и бюджета.
7. Публикация. Ждёт доступа.

## Что можно делать прямо сейчас, без ответов клиента

- выкачка каталога и фото: идёт;
- каркас первого лендинга;
- микроразметка;
- страница согласия, текст готов, ждёт публикации;
- превью на сайте отчёта;
- правки багов из `03_INSTRUCTIONS.md`.

## Что нельзя делать без ответа клиента

- принимать заявки: непонятно, куда;
- показывать цены: нужно подтверждение;
- публиковать на сайте клиента: нет доступа;
- запускать Директ: нет ключей и бюджета;
- ставить реквизиты ИП: не подтверждены.

## Чего не делаем никогда

- не публикуем внутренние отчёты с разбором багов на сайт отчёта;
- не переносим фото из старых архивов, берём свежие с сайта;
- не публикуем персональные данные ИП на публичном хостинге;
- не наследуем битые ссылки и дубли сайта клиента;
- не рисуем тридцать лендингов вслепую.
