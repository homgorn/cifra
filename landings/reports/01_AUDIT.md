## 2. Чем отличаются render.js и render-wp.js

Два рендера одного и того же `config.json`, дают **разные**
результаты.

`render.js`: статическая папка. На выходе `index.html`,
`styles.css`, `script.js`, `catalog.js`, `privacy.html`,
`backend/server.js`, `package.json`. Валидирует конфиг, падает на
отсутствии обязательных полей.

`render-wp.js`: один файл `content.html` с Gutenberg-блоками
`core/*` для импорта через WP All Import. Не пишет ничего, кроме
`content.html`. Конфиг **не** валидирует, при неполном молча
собирает полстраницы.

Договорённость «та же конфигурация, что и для статического сайта» из
README неполна: `render-wp.js` теряет `heroStats`,
`contactChannels` со всеми мессенджерами, аналитику, cookie-баннер,
JSON-LD, `privacy.html`. Hero-кнопки жёстко указывают `#quiz` и
`#catalog`, а `id="catalog"` в `content.html` не выставляется, то
есть якорь битый.

## 3. Блоки, которые надо починить

### 3.1 Квиз в render-wp.js скорее всего не работает

`script.template.js` один обработчик на всё, на `DOMContentLoaded`:

```js
renderCatalog(); initQuiz(); initForm(); ...
```

`renderCatalog()` начинается с `getElementById('catalog-container')`
и нигде не проверяет его на null. В `content.html`, который
собирает `render-wp.js`, каталог рендерится **без**
`id="catalog-container"`. Итог: `TypeError`, `initQuiz()` не
вызывается, обработчики отправки квиз-формы не навешиваются.

Даже с пустым каталогом следующий `initForm()` упал бы:
`#lead-form` в WP-версии тоже нет.

Вывод из чтения кода, ничего не запускалось. Но путь через
WordPress мы не выбираем, поэтому баг не критичен.

### 3.2 Цели Метрики зашиты на чужой счётчик

`script.template.js`, две строки:

```js
ym(12345678, 'reachGoal', 'quiz_submit')
ym(12345678, 'reachGoal', 'lead_submit')
```

`{{YMETRIKA_ID}}` подставляется только в HTML. Значит на всех
страницах цели уйдут в счётчик 12345678. Наш номер 50863157, он
лежит в `.env` как `METRIKA_COUNTER_ID` и подтверждён в разметке
сайта клиента.

Найдено в обоих блюпринтах и в `merch-landing-v2/script.js`.

Правки в `03_INSTRUCTIONS.md`, Правка 1-3.

### 3.3 Экранирование не трогает кавычки

`esc()` в `render.js` экранирует только `& < >`. Любая двойная
кавычка в `mapEmbedUrl`, `channel.url` или `item.img` ломает
атрибут.

Глубже: `script.template.js` собирает карточки через `innerHTML` с
полями `item.img`, `item.name`, `item.method`, `item.specs` без
экранирования. Конфиг из внешнего источника это вектор XSS.

`hero.h1` вставляется вообще без экранирования, и это записано как
«ответственность на конфиге».

### 3.4 Лиды с разных лендингов неразличимы

`server.template.js`, жёстко:

```js
SOURCE_DESCRIPTION: 'Лендинг {{BUSINESS_NAME}} — форма'
sourceDescription: 'Лендинг {{BUSINESS_NAME}} — квиз'
```

Подставляется только `business.name`. У календаря 2027 и у мерча
будет одинаковый `SOURCE_DESCRIPTION` и одинаковый заголовок.

С двумя лендингами терпимо, при масштабировании нет. Наша находка,
в `00_HANDOFF_LANDINGS.md` её нет.

### 3.5 Rate limit 5 в минуту на оба роута

`RATE_LIMIT_MAX = 5`, окно 60 секунд, счётчик один на процесс без
разделения по роутам. Пять промахов валидации, и посетитель
выжигает лимит себе же. Сам файл признаётся: работает только в
памяти одного процесса, для продакшена нужен Redis-бэкенд.

### 3.6 Остаточные плейсхолдеры не проверяются

`render.js` падает, если маркер отсутствует в шаблоне, но не падает,
если в выводе осталось `{{ЧТО-ТО}}`. Заявление README «ни одного
незамещённого плейсхолдера» в коде не зашито.

## 4. Конфигурация

### Обязательные, без них падает сборка

```
business.name, site.domain, meta.title, meta.description,
contact.phoneDisplay, contact.phoneTel, contact.email,
contact.address
```

### Опциональные, но нужны

- `business.legalEntity`: реквизиты оператора ПДн. Без них в футере
  и в политике текст «ИП/ООО не указано в конфиге, TODO».
- `contact.mapEmbedUrl`: iframe Яндекс.Карт.
- `contact.mapLat/mapLon`: кнопка «Проложить маршрут».
- `analytics.yandexMetrikaId`: счётчик, дефолт `00000000`.

### Поле, которого нет, а нужно

`landing.slug` и `landing.title`. Сейчас источник лида не содержит
идентификатора страницы. Для тридцати лендингов невозможно понять,
какая страница принесла лид.

### Поле, которое ничего не делает

`config.backend.bitrixWebhookEnvHint`: в примере есть, движком
не читается вообще. Реально подставляются только
`{{DEFAULT_MAIL_TO}}` и `{{BUSINESS_NAME}}`.

## 5. Что сделано хорошо и должно пережить правки

- **Бэкенд доставки.** Три канала через `Promise.allSettled`, `ok`
  если сработал хотя бы один, `502` только если упали все,
  `console.error` на любое упавшее звено, `process.exit(1)` с
  FATAL если не настроен ни один канал.
- **Ненастроенный канал бросает исключение, а не возвращает
  `null`.** Иначе `allSettled` засчитал бы провал успехом и лид
  пропал бы молча. Реальный баг, пойманный тестом на первой версии.
- **Honeypot** отвечает «успехом» без создания лида.
- **Квиз без цен** ведёт к «получить расчёт», а не считает сумму сам.
- **Запасной канал `mailto`** на шаге 4, работает даже если бэкенд
  недоступен.
- **Каталог вынесен в отдельный `catalog.js`**, экспортируется и как
  `module.exports`, и как `window.Catalog`.
- **Дизайн-токены с неизменёнными именами**: значения поменяны,
  имена старые. Полная перекраска без рефакторинга 300 строк CSS.
- **Graceful degradation**: `if (!window.gsap) return`, сайт
  полностью рабочий без CDN, `prefers-reduced-motion` в CSS.

## 6. Юридический слой: брать из демо, а не из мерча

В `merch-landing-v2` **нет**: чекбокса согласия, cookie-баннера,
страницы политики, реквизитов ИП в подвале, разметки
`LocalBusiness` и `FAQPage`. `.form-disclaimer` говорит про
обработку персональных данных без чекбокса и без ссылки, то есть
создаёт видимость согласия без согласия.

В демо-версии всё это есть. Значит юридический слой берём из демо,
мерч в этой части считаем устаревшим.

## 7. Что сломается при переносе в Битрикс

Риск №5 из `wordpress-spectra-astra-risks.md`: обычный хостинг
1С-Битрикс это PHP без Node, постоянный Node-процесс там не поедет.
Блюпринт даёт только вариант с отдельным Node.

Решается заменой `backend/server.js` на `php/lead.php`, спецификация
в `03_INSTRUCTIONS.md` часть 3.

Остальные риски из того файла относятся к WordPress и в нашем пути
не воспроизводятся: регенерация CSS Spectra, срезка заголовков
Application Passwords на шаред-хостинге, конфликт LiteSpeed-кэша.
