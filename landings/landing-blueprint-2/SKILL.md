# Landing Blueprint — квиз-лендинг по AIDA из URL

Обобщение рабочего паттерна (обкатан на лендинге «Цифра18», мерч-оффер,
Ижевск). Вход — один или несколько URL/файлов с описанием бизнеса. Выход —
готовый статический лендинг (`index.html`/`styles.css`/`script.js`/
`catalog.js`) + Node-бэкенд для приёма заявок.

## Когда использовать
- Дан URL сайта, PDF-презентация, прайс-лист или их комбинация
- Нужен именно ПРОДАЮЩИЙ одностраничник (не блог, не корпоративный сайт)
- У бизнеса есть каталог из нескольких товаров/услуг С переменными
  параметрами (тираж, объём, сложность) — тогда уместен блок 6 (квиз)
- Пользователь хочет повторяемость: "дам ещё URL — сделай так же"

## Workflow (шаги обязательны и по порядку)

### 0. Собрать вход
Спросить (одним сообщением, не растягивать на цепочку уточнений), если не дано:
- URL(ы) и/или файлы источника
- Контакты для приёма заявок: телефон(ы), email, адрес, CRM-вебхук (если есть)
- Домен будущего лендинга (для generic-текста типа "с сайта X")
Если что-то из этого не критично для старта (например, CRM) — не блокировать
работу, пометить как TODO и продолжить с email-каналом.

### 1. Извлечь факты (fetch/read), БЕЗ домыслов
- `web_fetch` каждый URL; для PDF/прайса — прочитать полностью, не выборочно
- Составить список: бизнес, что продаёт (категории + позиции), контакты,
  реальные УТП (только то, что явно написано, не "и наверное ещё
  быстро/качественно"), способы связи (мессенджеры — только с подтверждённой
  ссылкой/номером, не угадывать)
- Если сайт блокирует автоматический доступ (robots.txt) — сказать об этом
  прямо, не выдавать поисковые сниппеты за содержимое сайта без пометки

### 2. Зафиксировать пробелы вслух
Одним списком в ответе — что не нашлось в источнике (цены, конкретные цвета,
соцсети, SLA и т.п.). Это идёт в TODO шаблона, не в выдумку.

### 3. Спланировать блоки (`reference/aida-block-map.md`)
7-10+ смысловых блоков. Для каждого — конкретный источник факта. Показать
план пользователю кратко перед сборкой, если проект большой/неоднозначный.

### 4. Собрать `config.json` (см. `config.example.json`)
Один файл — вся бизнес-специфика. Ничего бизнес-специфичного не должно
лежать внутри `templates/`.

### 5. Определить, нужен ли квиз (`reference/quiz-calculator-pattern.md`)
Есть каталог + переменные параметры без фикс. цены → квиз (блок 6).
Простая услуга с понятной ценой → обычный прайс-блок вместо квиза,
`config.catalog` в этом случае можно не заполнять.

### 6. Рендер
```
node render.js config.json dist/
```
Смотри `render.js` — генерирует `index.html`, `styles.css`, `script.js`,
`catalog.js`, `backend/server.js`, `backend/package.json` из шаблонов +
конфига. Если рендер упал — чинить конфиг/шаблон, не редактировать
сгенерированный `dist/` вручную (при повторном рендере правки потеряются).

### 7. Самокритика и тесты (`reference/fact-checking-checklist.md`) — обязательно
- `node --check` на всех .js
- Кросс-проверка ID html↔js
- Живой curl-тест backend (health, validation fail, honeypot, оба канала
  недоступны → честный 502)
- Декодировать mailto-ссылки обратно, прочитать глазами

### 8. Сдача
Zip + `CHANGELOG.md` с явным списком: что взято из источника, что
предположение, что нужно от клиента (SMTP-доступ, CRM-вебхук, реальные
ссылки на мессенджеры и т.п.). Отчитаться о самокритике коротко в ответе,
не только в файле.

## Границы применимости
- Не подходит для многостраничных сайтов/каталогов на сотни SKU — это
  одностраничник с квизом до ~15-20 позиций каталога, дальше нужен полноценный
  e-commerce, не лендинг
- Не подходит, если у бизнеса УЖЕ есть фиксированный прайс на всё — тогда
  квиз не нужен, замени блок 6 на прайс-таблицу
- Способ доставки лида (email/CRM/мессенджер-бот) — под конкретного клиента,
  `backend/server.template.js` заточен под email+Bitrix24-подобный webhook,
  для другой CRM нужно писать свою функцию по образцу `createBitrixLead`
