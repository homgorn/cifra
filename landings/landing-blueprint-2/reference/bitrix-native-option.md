# Нативный Битрикс вместо WP-поддомена — что нашлось и почему это меняет рекомендацию

Контекст: основной сайт цифра18.рф уже на 1С-Битрикс (это объясняет и
структуру URL `/catalog/suvenirnaya-produktsiya/`, и блокировку robots.txt —
типично для этой CMS). Нужно ~30 лендингов ПО КАТЕГОРИЯМ ОДНОГО бизнеса
(не 30 разных компаний — это снимает большую часть риска дублей, см. ниже),
лиды должны уходить в их CRM.

## Важное терминологическое уточнение (легко перепутать)
«1С-Битрикс» (он же «Битрикс: Управление сайтом») — CMS, на которой стоит
сам сайт. «Битрикс24» — отдельный продукт (CRM/таск-трекер/сайты), облачный
или коробочный. Это разные вещи одной компании. Наш уже написанный
`createBitrixLead` в `backend/server.js` бьёт именно в REST API **Битрикс24**
(`crm.lead.add.json` по входящему вебхуку) — это работает независимо от того,
на чём сделан сам сайт, НО только если их «кастомная CRM» — это именно
Битрикс24, а не что-то полностью своё. Нужно подтвердить.

## Находка: у Битрикс24 есть нативные CRM-формы — могут заменить наш Node-бэкенд
В Битрикс24 есть встроенный конструктор «CRM-форма» (CRM > Продажи > Каналы
продаж > CRM-формы): визуально собираешь поля, выбираешь что создаётся (лид/
сделка/контакт), форму можно встроить на любую страницу блоком или получить
готовый embed-код. Если их CRM — Битрикс24, для ПРОСТОЙ формы (блок 9, без
квиза) это может целиком заменить наш `/api/lead` + `sendLeadEmail`/
`createBitrixLead` — просто вставляете их нативный виджет формы, лид летит
в CRM без единой строчки бэкенд-кода. Для КВИЗА (условная многошаговая логика)
нативная CRM-форма не подходит — там нужен кастомный JS, как у нас, и конечный
POST либо в их CRM-форму программно, либо через наш webhook-подход.

## Находка: типовой паттерн для «много похожих страниц» на 1С-Битрикс
Реальный разбор с Хабра (конкретно под задачу «100+ страниц с услугами,
шаблонные блоки, но не шаблонное расположение, заполняет контент-менеджер
без знания HTML»): делается ОДИН инфоблок («Лендинги» или «Услуги»), каждая
страница — элемент инфоблока со своими свойствами, один шаблон детальной
страницы читает свойства и рендerit нужные блоки, ЧПУ (человекопонятные урлы)
включается автоматически через компонент. **Это прямой аналог нашего
`config.json → render.js`** — только свойства инфоблока вместо JSON-полей,
и PHP-шаблон вместо `render.js`. Если решите делать нативно, "портировать"
то, что уже есть в `templates/`, на PHP-шаблон инфоблока — работа дней, не
недель: вёрстка/CSS/JS-движок квиза остаются ровно те же файлы, меняется
только то, ЧЕМ они наполняются (PHP вместо Node-скрипта).

## Почему это может быть лучше WP-поддомена для вашего конкретного случая
- **Одна из 30 страниц для ОДНОГО бизнеса** → дублей в смысле «разные
  компании с одинаковым текстом» нет в принципе (это было моим прошлым
  опасением, оно относилось к сценарию «десятки РАЗНЫХ клиентов» — для
  одного бизнеса по категориям риск только в том, чтобы категории
  различались по сути, а не просто по названию, что и так задаёт наш
  `config.catalog` на страницу).
- **Подпапка на основном домене** (`цифра18.рф/uslugi/suvenirka/` и т.п.)
  обычно консолидирует SEO-вес лучше, чем поддомен — поддомен Google
  исторически (и отчасти до сих пор на практике) может трактовать ближе к
  отдельному сайту, что для 30 страниц одного бизнеса — минус, не плюс.
- **Нет риска №1 из `wordpress-spectra-astra-risks.md`** (не генерируются
  стили блоков Spectra при импорте в обход редактора) — эта проблема вообще
  специфична для Gutenberg/Spectra, в 1С-Битрикс с PHP-шаблоном её нет.
- **Нет вопроса «где хостить Node»** — если PHP-эндпоинт живёт на том же
  сервере, что и сам Битрикс-сайт, это внутренний вызов, не нужен отдельный
  Node-процесс и не нужен CORS между доменами.

## Чего не хватает, чтобы решить окончательно
1. Их «кастомная CRM» — это Битрикс24? (если да — нативные CRM-формы решают
   часть задачи бесплатно, без кода)
2. Есть ли у вас/у кого-то доступ уровня разработчика к самому
   1С-Битрикс-сайту (создать инфоблок, залить PHP-шаблон), или доступ есть
   только к WP?
3. Технически возможно «портировать» наш блюпринт на PHP-шаблон инфоблока —
   но я не писал и не тестировал этот код: 1С-Битрикс специфичен (свой API
   для инфоблоков, `CIBlockElement`, `bitrix:news.detail` или кастомный
   компонент), и без доступа к реальной инсталляции для проверки это были бы
   непротестированные предположения, а не проверенный код, как всё остальное
   в этом блюпринте.
