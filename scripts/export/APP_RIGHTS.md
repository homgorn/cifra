# Права приложения: полный список

Список снят с настроек приложения на `oauth.yandex.ru` и зафиксирован
здесь, потому что он единственный авторитетный источник имён прав.
Всё, что связано со `scope` в ссылке авторизации, должно ссылаться на
этот файл, а не на память.

Приложение типа **«Для доступа к API»**. Тип важен: такие приложения не
могут получать права группы `login`, поэтому `login:info` и
`login:email` в ссылке недопустимы в принципе. Именно этим был вызван
первый `invalid_scope`, и на него было потрачено несколько итераций.

## Что объявлено

| Право | Описание из панели | Берём | Зачем |
|---|---|---|---|
| `metrika:read` | Получение статистики, чтение параметров своих и доверенных счётчиков | да | вся Метрика проекта |
| `webmaster:verify` | Добавление сайтов в Вебмастер, получение информации о статусе индексирования | да | это и есть чтение статуса |
| `webmaster:hostinfo` | Получение информации о внешних ссылках на сайт | да | внешние ссылки, дало LINKS_TOTAL_COUNT |
| `mediametrika:read` | Получение статистики, чтение параметров рекламодателей и кампаний | да | конверсии в отчётах Директа |
| `direct:api` | Использование API Яндекс.Директа | да | весь Директ |
| `metrika:write` | Создание счётчиков, изменение параметров своих и доверенных счётчиков | нет | проект только читает |
| `metrika:user_params` | Загрузка параметров пользователей | нет | не используется |
| `metrika:segments` | Управление сегментами пользователей | нет | не используется |
| `metrika:offline_data` | Загрузка офлайн данных: CRM, офлайн-конверсии, звонки | нет | CRM ещё нет |
| `metrika:expenses` | Загрузка расходов | нет | расходы берём из Директа |
| `webmaster:turbopages` | Добавление Турбо-страниц | нет | не используется |
| `mediametrika:write` | Создание рекламных кампаний | нет | не используется |
| `suggest:read_web_history` | Чтение истории запросов | нет | не используется |
| `maps:public_bookmarks` | Доступ к закладкам в Картах | нет | не используется |

## Что запрашивается в ссылке

```
metrika:read,webmaster:verify,webmaster:hostinfo,mediametrika:read,direct:api
```

Только чтение. Лишние права не запрашиваются: расширяют то, что видит
токен, и по документации Яндекса добавление прав может сокращать срок
жизни токена. `metrika:write` позволяет менять счётчики, а
`mediametrika:write` создавать кампании, и оба опасны без нужды.

Значение хранится в `scripts/export/yandex_oauth.py`, константа
`SCOPES`, переопределяется через `YANDEX_SCOPES` в `.env` и флагом
`--scope=...` на одну попытку.

## Счётчика сайта у аккаунта исполнителя нет

Уточнение от 30 сентября 2026, сообщил пользователь: в его Метрике есть
только счётчик `59102713`, карточка в Яндекс Бизнесе. Счётчика сайта
`50863157` у него нет, и в списке доступных счётчиков его тоже нет.

Отсюда следует, что блокирующая проблема простая и не про права
приложения: счётчик сайта не открыт аккаунту исполнителя. Никакой токен
это не обходит, потому что список счётчиков формируется по доступу
аккаунта, а не по правам токена.

Отсюда же объясняются выгрузки от 27 сентября: они сделаны токеном
`izhcifra`, что и записано в `.env` как `YANDEX_ACCOUNT_EMAIL`. Токен
исполнителя в проекте данные сайта не читал и раньше, просто это не
сверялось.

Что нужно сделать, описано в `CLIENT_ACCESS.md`: владелец счётчика
открывает `metrika.yandex.ru`, счётчик `50863157`, Настройка, Доступы и
добавляет аккаунт исполнителя с правами «Просмотр». После этого
`50863157` появляется в списке счётчиков, и это видно без переписки.

## Что из прежних объяснений оказалось не про то

Счётчики со значением `source: sprav` в списке это счётчики справочника
Яндекс Бизнеса, а не сайтов. Их `403` на отчётах стоял рядом со счётом
сайта как признак отсутствия прав вообще, а это разные вещи: по
справочнику отчёты и не обязаны отдаваться так же.

Гипотеза про `passport:business` и организацию, скорее всего, была не
про то. Право в списке есть, и причина не в нём. Счётчик Dzen
`109075324` с `permission: own` и 403 на отчётах остаётся отдельным
вопросом и работу не блокирует.

## Состояние на 30 сентября, вечер: доступ к счётчику открыт

Счётчик сайта появился в списке доступных, значит клиент подключил аккаунт:

| Счётчик | В списке | Право | Владелец |
|---|---|---|---|
| `50863157` сайт | **да** | **analyst** | izhcifra |
| `109075324` Дзен | да | own | refertur |
| `59102713` карточка | да | view | системный |
| `88507836` | да | view | системный |
| `97202764` | да | view | системный |

Токен менять не нужно, доступ виден текущим токеном и без перевыпуска,
потому что доступ к счётчику это свойство аккаунта, а не токена.

По справке Метрики уровня «Аналитика» достаточно для просмотра
статистики: он разрешает создавать цели и сегменты и сохранять отчёты.
Значит этого уровня должно хватать.

## Что осталось незакрытым

Отчёты отдают 403 на всех пяти счётчиках, включая `109075324`, которым
аккаунт владеет. Управление счётчиками при этом работает целиком.

Разбор причин 403 из справки Метрики, проверено по одной:

| Причина из документации | Проверка | Итог |
|---|---|---|
| У приложения нет `metrika:read` | есть в выданных правах | нет |
| Токен недействителен | управление работает | нет |
| Токен от другого аккаунта | счётчики видны, права analyst | нет |
| Токен от другого приложения | тот же, что и работающий | нет |
| Нет доступа к счётчику | analyst получен | нет |
| Неверные параметры авторизации | заголовок как в документации, управление проходит | нет |

Все шесть причин из справки сняты, отчёт при этом не отдаётся. Значит
либо причина в списке неполон, либо поведение отличается от описанного.

## Токен владельца: отказ общий, а не по счётчику

Получен токен от аккаунта `izhcifra`. Префикс другой, `y0__wgBEN-`
против `y0__wgBEL-`, и список счётчиков сократился до двух, то есть
аккаунт сменился. Права на счётчик сайта:

| Поле | Значение |
|---|---|
| `owner_login` | izhcifra |
| `permission` | **own** |
| `status` | Active |
| `accounts` | пусто, привязки к организации нет |

Полный владелец счётчика, без гостевых прав, и отчёты всё равно
`403 access_denied`.

## Отказ не различает счётчики

Запрос к заведомо несуществующему счётчику `99999999` даёт тот же
ответ, байт в байт. Значит отказ общий на сервисе отчётов, и по коду
ответа судить о доступе к конкретному счётчику нельзя.

## Что исключено окончательно

| Версия | Почему исключена |
|---|---|
| Не тот аккаунт | проверено и на исполнителе, и на владельце |
| Не тот токен | токен владельца выдан заново, другой префикс |
| Нет доступа к счётчику | `permission: own`, полный владелец |
| Привязка к организации | `accounts` пуст |
| Не то приложение | смена приложения сегодня не изменила результат |
| Нет `metrika:read` | право выдано, проверялось отдельно |
| Неверные параметры запроса | шесть форм запроса, все дают 403 |

Всё, что проверяется со своей стороны, проверено. Остаётся причина на
стороне Яндекса: доступ приложения к отчётному сервису Метрики.

## Побочный эффект проверки scope, который пришлось откатить

С токеном, выданным со `scope=metrika:read`, Вебмастер перестал
работать совсем: `HTTP 403` с текстом «Access to this resource is not
allowed with scopes available for this application». То есть перечень
в ссылке работает как ограничитель: названное право сохраняется, все
неназванные отваливаются.

По умолчанию scope снова не передаётся, Вебмастер работает. Просить
scope ради одного сервиса нельзя, это ломает остальные.

Открыть обращение в поддержку, со ссылкой на этот раздел. Приложение
зарегистрировано верно, права выданы, аккаунт владеет счётчиком, токен

Попутно проверить, не требует ли приложение верификации. В документации
Яндекс ID есть раздел о подтверждении аккаунта, и доступ к части API
сервисов открывается только верифицированным приложениям.

## Причина найдена, и она описана в документации Яндекса дословно

Поиск по похожим сбоям, 54 запроса плюс официальные страницы, привёл к
прямому совпадению. Документация Яндекс Метрики, раздел «Возможные
проблемы и их решение», блок «Ошибка 403 (Access is denied) после
получения токена», группа «На стороне токена»:

> **Токен создан не для того приложения.** При выполнении GET-запроса на
> получение токена в параметре `client_id` было указано не то значение
> или была допущена опечатка, из-за которой токен был заведён на
> приложение, не имеющее доступа к Метрике (`metrika:read` или
> `metrika:write`).

Там же, группа «На стороне приложения»:

> **Приложение не имеет доступа к Метрике.** Для чтения данных счётчиков
> (построение отчётов, просмотр информации по счётчику и т.п.) нужен
> доступ `metrika:read`.

## Что не сходилось у нас, и теперь сложилось

| Наблюдение | Как объясняет причина из документации |
|---|---|
| `management/v1/counters` отдаёт 200 | список счётчиков не требует `metrika:read` на уровне приложения |
| `stat/v1/data` отдаёт 403 на любой счётчик | отчётный сервис требует `metrika:read`, которого у приложения нет |
| счётчик `99999999` даёт тот же ответ байт в байт | отказ случается до проверки номера счётчика, поэтому номер безразличен |
| `permission: own` у владельца | право на счётчик настоящее, оно ни при чём |
| `accounts` пуст | привязки к организации нет, она ни при чём |

Последние две строки и есть тот факт, который я принял за
опровержение. Отказ по приложению снаружи неотличим от отказа по
счётчику, и `permission: own` их не различает.

## Ещё два документированных механизма отзыва, которые это объясняют

Страница «Отзыв токенов» Яндекс ID, дословно:

> Владелец приложения **изменил запрашиваемые права** либо удалил
> приложение. В этом случае **отзываются все токены, когда-либо
> выданные этому приложению**.

Права сегодня менялись, добавлялись `passport:business`,
`clients:priority.api`, `webmaster:hostinfo`. По этому правилу все ранее
выданные токены этого приложения отозвались в тот момент. Это отдельно
объясняет найденный в интернете случай «сначала работало, потом
перестало»: у человека в Клубе Метрики было именно так, и первый ответ
сотрудника Яндекса был про срок жизни токена.

Вторая строка той же страницы:

> У приложения не может быть больше 30 токенов, привязанных к
> устройствам определенного пользователя. Если Яндекс OAuth успешно
> выдает приложению новый токен для устройства, **самый старый из таких
> токенов перестает работать**.

Там же перечислены действия, отзывающие все токены аккаунта сразу:
смена пароля, включение или выключение двухфакторной аутентификации,
восстановление доступа, выход по ссылке «Выйти везде».

## Гипотеза про IP отпадает

Управление счётчиками и отчёты идут с одного адреса
`api-metrika.yandex.net`, тем же токеном и с того же IP. Если бы
блокировала сеть или адрес, отказали бы оба. Отказывается ровно один,
отчётный. Признаков блокировки в ответах нет: ни кодов 429, ни
заголовков о превышении лимита, тело ответа стандартное для Метрики.

## Обходной путь через Logs API не существует

Найдено подтверждение: «Logs API понадобится тот же токен, что и для
доступа к API отчетов». Отдельного токена у Logs API нет, поэтому обойти
отказ он не может.

## Про Директ: отказ ожидаемый, и срок известен

Код `58` в справочнике Директа означает «Незавершённая регистрация.
Необходимо создать заявку на доступ к API и дождаться её
подтверждения». Это не ошибка, это процедура. Сроки на странице
«Заявка на доступ»:

> Рассмотрение заявок производится в рабочие дни РФ с 10:00 до 19:00.
> Обработка заявки занимает от часа до трёх суток в рабочие дни.

Из практики сторонних разработчиков: песочница Директа тоже требует
одобренной заявки, обходного пути нет, повторная авторизация
возвращает ту же ошибку 58. Значит ждать действительно нужно.

| Что | Зачем |

## Проверка решающая, 1 октября: свежий токен от владельца

Владелец проекта подтвердил, что живое приложение это
`68e7441ebf904066a198d75cb2cfc9bd`, то есть то, что уже было в `.env`
и на которое вели все напечатанные ссылки. Версия «не то приложение»
снята.

Дальше: кодовый обмен требует секрет приложения, которого в `.env` нет,
поэтому перешли на неявный поток, секрет не нужен вовсе. Владелец
выдал токен заново, после всех правок прав, и вот что измерено тем
же токеном:

| Проверка | Результат |
|---|---|
| `management/v1/counters` | 200, два счётчика, `izhcifra` |
| `management/v1/counter/50863157` | 200, `permission: own` |

Счётчика два, и это аккаунт владельца, не исполнителя: счётчик сайта и
карточка организации. Счётчики Дзена и чужих карточек, которые были видны
по токену исполнителя, исчезли. Аккаунт сменился, это подтверждено.

Токен свежий, выдан сегодня после всех изменений прав. Право на счётчик

## Что осталось непроверенным, и это единственное

Одно: объявлено ли у приложения `68e7441e` право
`metrika:read`, то есть строка «Получение статистики, чтение параметров
своих и доверенных счётчиков» в «Доступ к данным» на
`oauth.yandex.ru`. Запросом это не проверяется, список прав лежит в

| Ответ | Что это значит |
|---|---|
| строки нет | причина найдена, приложение просто не объявило право |
| строка есть | отказ на стороне Яндекса, писать в поддержку |

Второй случай оформлен: команда `probe_metrika.py` собирает текст
обращения из того, что реально измерила, включая `client_id`, право на
счётчик и владельца. Ничего в тексте не зашито руками.

## Ошибка в `paste`, пойманная на живом токене

Команда `paste` сохраняла токен в `.env` и тут же проверяла права, но
проверяла по окружению, прочитанному при запуске процесса. Токен
записывался правильно, а вывод показывал права предыдущего. На первом
же прогоне пришлось увидеть `...IQG4` вместо только что присланного
`...cn7f`.

Это ровно тот класс ошибок, который самый дорогой: вывод выглядит
правдоподобно и относится не к тому, что проверяли. Теперь `paste`
перечитывает `.env` после записи.

## Демо-счётчик: вывод слабее, чем показалось

Проверялся счётчик `44147844` из справки Метрики, на который у токена
нет никаких прав. Ответ тот же `403 access_denied`, и из этого был сделан

Вывод логически неполон. Тот счётчик открыт как учебный дашборд в
интерфейсе, а доступность его через API никто не проверял. Если такие
счётчики по устройству не отдаются в API, тест ничего не различает, и
правильный вывод из него противоположный: непроверенный контрольный
объект нельзя использовать как эталон.

Вывод, который из него следует и который проверен: раз доступность
эталонного счётчика неизвестна, проверить сервис по нему нельзя.
Единственный надёжный признак это список доступных счётчиков, он и был
принят в расчёт.

## Scope с response_type=token не сработал

Запрошено `metrika:read` вместе с `response_type=token`. Яндекс вернул
тот же токен, что уже лежал в `.env`, то есть уже выданный действующий,
и права в него не подставились. Скрипт это ловит и останавливается с
кодом 4, файл не перезаписывается.

Отсюда: чтобы новые права попали в токен, старый надо отозвать и взять
новый. Пока старый жив, `response_type=token` возвращает именно его.

## Дальнейший ход, от порядка действий

Порядок тот же, что и раньше, но каждый шаг теперь закрывается сразу
и не требует догадок.

1. Отозвать токен на `id.yandex.ru/personal/data-access`.
2. Взять токен заново, ссылка теперь несёт `scope=metrika:read`
   вместе с `response_type=token`.
3. Проверить: `python scripts\export\yandex_oauth.py test`.

Если после этого отчёты всё ещё 403, остаётся одно действие,
и оно снимает сразу все оставшиеся неизвестные: **пусть сам токен
выдаст владелец.** Владелец аккаунта `izhcifra` открывает ту же ссылку
и подтверждает доступ. У владельца максимальные права на счётчик, ему не
нужны ни добавления в список доступов, ни права организации, ни область
scope. Токен, выданный владельцем, это то же, чем делались выгрузки
27 сентября, и он точно читает отчёты.

Проект изначально рассчитан именно на это: `YANDEX_ACCOUNT_EMAIL` в
`.env` это `izhcifra@yandex.ru`, а не аккаунт исполнителя. Токен
исполнителя пробовали весь день, и он не даёт отчётов ни при какой
конфигурации.

## Тест, который разделит это за один шаг

Открыть `metrika.yandex.ru` под аккаунтом исполнителя и посмотреть
статистику любого счётчика в браузере.

Видно в браузере, но не через API: дело в токене или в правах приложения,
и чинить надо приложение.

Не видно и в браузере: дело в доступе или в привязке счётчика к
организации, и API тут ни при чём, а все сегодняшние версии про scope
и токены были не туда.

Из справки про ошибки есть отдельный тип `counter_in_connect`: счётчик
привязан к организации в Яндекс Коннекте, и индивидуальными доступами
можно управлять только в веб-интерфейсе Коннекта. Наш ответ
`access_denied`, а не `counter_in_connect`, но сама привязка к
организации в данных видна: `accounts` возвращает организацию
`izhcifra`, а счётчик имеет владельца `izhcifra`.

## Чего в списке не хватает: passport:business

Счётчики Метрики в этом проекте принадлежат не личному аккаунту, а
организации. Это видно без всяких догадок:

```
GET /management/v1/accounts
200  {"accounts":[{"user_login":"izhcifra","uid":728896863,
                   "created_at":"2026-09-23T12:30:01+03:00"}]}
```

Счётчик сайта `50863157` имеет `owner_login: izhcifra`, счётчик карточки
и счётчик Dzen созданы в том же контексте, и сессия `refertur` работает
через организацию `izhcifra`.

Документация Метрики, раздел «Получение OAuth-токена», говорит прямо:

> Если вы работаете через porg-логины (логины организации), то в правах
> доступа добавьте **passport:business**, это необходимо для выдачи
> токена от организации.

Права `passport:business` в списке приложения **нет**. Это и есть
причина отказа.

## Как это проявляется

| Что | Результат |
|---|---|
| `management/v1/counters` | 200 |
| `management/v1/counter/<id>` | 200 |
| `management/v1/counter/<id>/goals` | 200 |
| `management/v1/counter/<id>/filters` | 200 |
| `management/v1/counter/<id>/segments` | 200 |
| `management/v1/counter/<id>/operations` | 200 |
| `management/v1/counter/<id>/access_filters` | 200 |
| `management/v1/delegates` | 200 |
| `management/v1/accounts` | 200, организация `izhcifra` |
| `stat/v1/data` | **403** |

Управление работает целиком, отчёты не работают ни по одному счётчику,
включая счётчик, которым владеет сам аккаунт токена. Это подпись токена,
выданного личному аккаунту при работе с счётчиками организации: права на
управление есть, право на отчёты требует `passport:business`.

## Что сделать

1. `oauth.yandex.ru`, настройки приложения, добавить право
   **`passport:business`**. Если такого права нет в списке доступных,
   значит приложение зарегистрировано не как «Для доступа к API», а тип
   приложения после регистрации не меняется, и тогда нужно новое
   приложение.
2. Взять токен заново: `python scripts\export\yandex_oauth.py login`.
3. Проверить: `python scripts\export\yandex_oauth.py test`.

Вебмастер эта право не требует. Он работает по доступу к сайту, а не по
организации, поэтому читался при том же токене, который не может читать
отчёты Метрики.
