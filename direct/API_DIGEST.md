# Директ: что есть в API и как это связать с остальным

Снимок документации на 30 сентября 2026. Источник: `yandex.ru/dev/direct`,
версия API 5, отчёты версии 501. Полный индекс документации Яндекс
отдаёт сам, файл `llms.txt` в корне раздела.

## 1. Три вещи, которые надо сделать, прежде чем заработает

Порядок именно такой, каждый шаг без следующего бессмыслен.

**1. Приложение зарегистрировано.** Уже сделано, новый `client_id`
`68e7441e...` в `.env`.

**2. Подана заявка на доступ к API Директа.** Это отдельная процедура от
добавления права в приложении. Заявка подаётся на странице
`direct.yandex.ru/registered/main.pl?cmd=apiCertificationRequestList`,
вкладка «Мои заявки». На одно зарегистрированное приложение подаётся
одна заявка, сколько бы пользователей ни работало. Срок рассмотрения
от часа до трёх суток в рабочие дни, в периоды высокой нагрузки до семи
суток.

**3. Пользователь принял условия соглашения** на
`direct.yandex.ru/registered/main.pl?cmd=apiSettings&api_welcome=yes` и
разрешил приложению доступ.

Пока не выполнены пункты 2 и 3, любой вызов отдаёт код `58`: «нужно
подать заявку на доступ к API в интерфейсе Директа и дождаться
подтверждения». Проверено на живом токене 30 сентября 2026.

## 2. Схема заголовка: Bearer, а не OAuth

В документации написано `Authorization: OAuth <токен>`. Фактически
нужен `Authorization: Bearer <токен>`.

Проверено на одном и том же токене, одном запросе `Clients.get`,
30 сентября 2026:

| Схема | Ответ |
|---|---|
| `OAuth` | код `8000`, текст «OAuth token is missing» |
| `Bearer` | код `58`, текст про неподанную заявку на доступ |

Ошибка `8000` утверждает, что токен не прислан, хотя он прислан. Из-за
этого уходит в сторону: дело в схеме заголовка, а сообщение говорит про
токен. Схема `Bearer` проходит дальше по проверке прав и называет
настоящую причину. В клиенте используется `Bearer`, и код `8000` с
текстом «token is missing» в списке расшифровок помечен именно как
признак неверной схемы.

## 3. Адреса

| Что | Адрес |
|---|---|
| Методы сервисов | `https://api.direct.yandex.com/v5/<Сервис>/<метод>` |
| Отчёты, JSON | `https://api.direct.yandex.com/json/v501/reports` |
| Песочница, методы | `https://sandbox.direct.yandex.com/v5/<Сервис>/<метод>` |
| Песочница, отчёты | `https://sandbox.direct.yandex.com/json/v501/reports` |
| XSD для XML | `https://api.direct.yandex.com/v501/reports.xsd` |

Все запросы это POST. Тело и ответ в JSON, кроме отчётов, которые
возвращаются вложением в формате TSV. Кодировка UTF-8.

Ошибки сервер отдаёт конвертом SOAP `<SOAP-ENV:Fault>` с кодом
`<errorCode>` внутри и текстом `<errorDetail>`, причём **с кодом
HTTP 200**. Успешный HTTP-ответ не значит успешный вызов, и разбор тела
обязан понимать оба вида. Клиент это учитывает.

## 5. Отчёты: типы и что они дают

| ReportType | Что считает | Группировка |
|---|---|---|
| `ACCOUNT_PERFORMANCE_REPORT` | по аккаунту | нет |
| `CAMPAIGN_PERFORMANCE_REPORT` | по кампаниям | CampaignId |
| `ADGROUP_PERFORMANCE_REPORT` | по группам | AdGroupId |
| `AD_PERFORMANCE_REPORT` | по объявлениям | AdId |
| `CRITERIA_PERFORMANCE_REPORT` | по условиям показа | AdGroupId, CriteriaId, CriteriaType |
| `CUSTOM_REPORT` | произвольные группировки | нет |
| `SEARCH_QUERY_PERFORMANCE_REPORT` | по поисковым запросам | AdGroupId, Query |
| `REACH_AND_FREQUENCY_PERFORMANCE_REPORT` | медийные кампании | CampaignId обязателен |

Обязательные параметры: `FieldNames`, `ReportName`, `ReportType`,
`DateRangeType`, `Format` (только `TSV`), `IncludeVAT`.
`DateFrom` и `DateTo` обязательны только при `CUSTOM_DATE` и недопустимы
при других значениях `DateRangeType`.

## 6. Баллы, без которых не начинать

Баллы регулируют нагрузку на сервер. При их нехватке запрос не
выполняется, приходит код `152`. Баллы списываются и за успешные
вызовы, и **за вызовы, завершившиеся ошибкой**, по 20 баллов.

Суточный лимит скользящий, разбит на 24 часовых интервала, в начале
каждого начисляется 1/24 лимита плюс нерасходованное за предыдущие 23
часа. Начало интервала не совпадает с астрономическим часом.

В каждом ответе приходит заголовок:

```
Units: израсходовано/остаток/суточный_лимит
```

Например `Units: 10/20828/64000`. Заголовок обязателен к чтению: без
него причина ошибки 152 неочевидна. Клиент проверяет остаток до запроса
и останавливается, не потратив остаток впустую.

Не более пяти одновременных запросов к API от одного рекламодателя.

## 7. Ограничения отчётов

- Не более **20 запросов к Reports за 10 секунд** на пользователя.
- В очереди одновременно не более **5 офлайн-отчётов** на пользователя.
- Сформированные офлайн-отчёты хранятся **5 часов**, потом удаляются.
- Статистика доступна за последние **3 года**.
- Поле `Query`, то есть сам поисковый запрос, доступно только за
  последние **180 дней**. Это единственный мост к данным Вебмастера,
  и он не бесконечный: годовая выгрузка по запросам невозможна,
  придётся копить помесячно.

Режим формирования задаётся заголовком `processingMode`:
`online`, `offline` или `auto` (по умолчанию). Ответы:

- `200` отчёт готов и лежит в теле;
- `201` отчёт поставлен в очередь;
- `202` ещё формируется, прийти позже;
- `400` ошибка параметров либо превышен лимит очереди;
- `500` ошибка на сервере.

При `201` и `202` в ответе есть заголовок `retryIn` с числом секунд,
через которое нужно повторить запрос с теми же параметрами.

Отчёты типа `SEARCH_QUERY_PERFORMANCE_REPORT` формируются
**только в офлайн-режиме**, это не сбой.

## 8. Данные Метрики внутри отчётов Директа

В отчётах Директа есть поля, посчитанные по данным Метрики: `Sessions`,
`AvgPageviews`, `Bounces`, `BounceRate`, `Conversions`,
`ConversionRate`, `CostPerConversion`, `Revenue`, `Profit`, `GoalsRoi`.

Условия появления этих полей, все четыре нужны одновременно:

1. счётчик Метрики установлен на сайте;
2. номер счётчика указан в параметре кампании `CounterIds`;
3. цели настроены на счётчике;
4. цели помечены как ключевые в настройках кампании, либо код счётчика
   передаёт стоимость заказа.

Если хотя бы одно не выполнено, поля пустые и выглядят как ноль
конверсий. Для проекта это значит, что деньги из Директа нельзя
считать окупаемыми, пока не проверено, что `CounterIds` проставлены.

Параметр `Goals` в отчёте подставляет цели Метрики по идентификаторам,
не более десяти за раз. Поля при этом переименовываются в
`<поле>_<id_цели>_<модель_атрибуции>`.

Модели атрибуции: `FCCD`, `LC`, `LSCCD`, `AUTO`, по умолчанию `LC`.
Устаревшие `LSC`, `FC`, `LYDC`, `LYDCCD` конвертируются автоматически
с предупреждением.

Данные Метрики в отчётах Директа могут отставать на несколько часов:
данные счётчиков нужно сопоставить с кампаниями.

## 9. Где мост между Директом, Вебмастером и Метрикой

Это то, ради чего всё затевалось. Три источника, у каждого своя
половина картины, и стыкуются они по тексту запроса.

| Источник | Что знает | Ключ |
|---|---|---|
| Вебмастер | органическая позиция, показы, клики | текст запроса |
| Директ | рекламная позиция, цена, клики, какая фраза оплатила показ | текст запроса |
| Метрика | визиты, отказы, глубина, выручка по источнику | источник трафика |
| Topvisor | входит ли запрос в семантическое ядро | текст запроса |

Поле `Query` в `SEARCH_QUERY_PERFORMANCE_REPORT` даёт реальный запрос,
по которому было показано объявление. Поле `MatchedKeyword` даёт фразу,
которая за него заплатила. Вместе они отвечают на вопрос, который
ни Вебмастер, ни Метрика по отдельности не отвечают: **за какую фразу
платит клиент и какую позицию занимает бесплатно.**

`Keyword` в отчётах Директа помечена как фильтр: в столбцы не
выводится. `Criteria` и `CriteriaId` группируют по условию показа,
`Criterion` и `CriterionId` то же, но по условию, заданному
пользователем, и в документации прямо сказано использовать их вместо
первых двух.

Практический вывод, который даёт сочленение: если по запросу
органика уже в топ-5, а Директ по нему всё равно платит, деньги
идут на позицию, которая уже занята. Это видно только в объединённой
таблице, в панели Директа такой строки нет.

## 10. Стоимость в микроединицах

Денежные значения по умолчанию приходят целым числом, умноженным на
миллион, то есть 1 450 000 это полтора миллиона рублей в понимании
сервера и полторы тысячи в человеческом. Заголовок
`returnMoneyInMicros: false` заставляет отдавать рубли. Клиент ставит
его всегда, включая в отчёты, где он тоже поддерживается.

## 11. Что проверить при первом запуске

1. Что в `.env` лежит `DIRECT_OAUTH_TOKEN`, а не только общий
   `YANDEX_OAUTH_TOKEN`. Один токен на все сервисы удобен, но ошибиться
   в аккаунте легче, а ошибка выглядит как «нет доступа».
2. Что `Clients.get` возвращает логин того аккаунта, которому
   принадлежит ЦИФРА.
3. Что `Campaigns.get` находит кампании, а не пустой список.
4. У кампаний проставлен `CounterIds`, иначе конверсий не будет.
5. Остаток баллов в заголовке `Units` и суточный лимит.
